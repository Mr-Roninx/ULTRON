## 1. Top-Line Assessment (Plain English)

If you clone this repository today, install dependencies (`npm install` in root and `frontend/`), and start both services (`npm start` and `npm run dev` in `frontend/`), **the application starts immediately without errors**. The backend initializes an embedded SQLite database (`ultron.db`), establishes an Express API on port 3001, and exposes all 7 pipeline endpoints alongside an active fallback reconciliation loop. The frontend runs Next.js (Turbopack) on port 3000, serving an interactive single-page dark-mode dashboard that auto-polls the backend every 3 seconds. When you trigger the pipeline (or run `npm run seed` followed by the test suite), ULTRON deterministically scores recovery opportunities using counterfactual economics ($\text{IVEN}$), runs a greedy market allocation constrained to 5 payment links, executes an independent 5-check Action Authority compliance gate, and calls Razorpay's live Test Mode API to generate genuine hosted payment links (e.g. `https://rzp.io/rzp/F8WXnuR`). However, **the loop ends at link generation**: the system has never processed a genuine inbound payment webhook from a completed customer checkout on Razorpay's hosted gateway; all "recovered" states in the audit history were generated by local test scripts POSTing self-signed webhook payloads to `localhost:3001`.

## 6. Specification vs. Reality Behavioral Diff

### 1. Strict Financial Accounting Boundary
- **Doc Claim**: The "$ Recovered" dashboard KPI reflects strictly real, reconciled payments, never synthetic estimations.
- **Reality**: **VERIFIED IN LOGIC, BUT VULNERABLE TO LOCAL SIMULATION INGESTION**.
  - In `src/routes/dashboard.ts`, `total_recovered_paise` strictly computes:
    ```ts
    const realRecoveredOpps = allOpps.filter((o) => o.source === 'real' && o.status === 'recovered');
    ```
  - Synthetic opportunities (`source = 'synthetic'`) that are recovered are stored in `synthetic_recovered_paise` and excluded from `total_recovered_display`.
  - **However**, `src/perception/normalizer.ts` hardcodes `source = 'real'` for ANY payload received at `/webhooks/razorpay`. When local test scripts (`test_webhook.ts` or `test_truth_engine.ts`) POST mock payloads to this endpoint, they are classified as `source = 'real'`, allowing simulated test payments (`pay_test_failed_001`) to count toward the "real" recovered total.

### 2. Action Authority `confidence_recheck` Reachability
- **Doc Claim**: Check 4 (`confidence_recheck`) acts as an independent compliance safety gate that vetos low-confidence opportunities.
- **Reality**: **REDUNDANT IN STANDARD PIPELINE RUNS**.
  - In `src/market/allocator.ts`, the Recovery Market pre-filters `if (score.confidence === 'low')` directly into `ABSTAIN` before ranking begins.
  - Consequently, **no opportunity marked `ACT` by the Market can ever reach Action Authority with `confidence = 'low'`**.
  - When `runAuthorityPipeline()` iterates across all opportunities, `confidence_recheck` records `passed = false` for opportunities that were **already marked `ABSTAIN`** by the Market (such as `synth_unmapped_reason_test`). It never acts as a veto against an `ACT` decision in normal pipeline execution. It only functions as a safety net if an external caller bypasses the Market stage and passes an unallocated item directly to `evaluateOpportunity()`.

### 3. Evaluation Scope of Action Authority
- **Doc Ambiguity**: Architecture diagrams imply Authority evaluates only `ACT` items, while prose states it checks all opportunities.
- **Reality**: In `src/authority/gate.ts` (lines 195–218), `runAuthorityPipeline()` iterates over **all opportunities in the database** (`allOpps`). For `WAIT` items, check 5 (`capacity_recheck`) records `passed = false` ("not within active market allocation batch") and outputs verdict `WAIT`. For `ABSTAIN` items, check 4 or check 5 records `passed = false` and outputs verdict `ABSTAIN`.

## 8. What Is Genuinely Solid

Despite the lack of an end-to-end completed customer checkout from the external internet, the core architectural foundations of ULTRON are robust, rigorous, and completely intact:

1. **Two-Stage Architecture Cleanly Partitioned**:
   - The economic reasoning layer (`src/market/allocator.ts`) and the deterministic compliance gate (`src/authority/gate.ts`) are separated into two distinct stages. The market stage ranks by $\text{IVEN}$ and stamps shadow price without baking in hardcoded compliance vetoes. The authority stage enforces 5 deterministic checks with hard veto powers.
2. **Mathematical Precision & Single Point of Truth**:
   - $\text{IVEN}$ is calculated strictly in `src/economics/scorer.ts` using floating-point probabilities converted to exact integer paise. No downstream module recalculates or alters the formula.
3. **Zero-LLM Execution Guarantee**:
   - There are **zero LLM call sites** in the active `src/` directory. All decisions, rankings, checks, and API calls are 100% deterministic TypeScript.
4. **Idempotency & Zero-Bypass Enforcement**:
   - `src/execution/executor.ts` explicitly asserts `evalResult.verdict === 'AUTHORIZED'` before initializing any Razorpay API call. Passing a blocked or deferred opportunity throws an immediate compliance violation. Payment link creation is strictly idempotent via `reference_id = opp.id`.
5. **Real Razorpay SDK Integration**:
   - When given authorized opportunities, the system successfully connects to Razorpay Test Mode APIs using genuine credentials and creates valid, hosted payment links that can be opened in any web browser.
6. **Stored-Field Forensic Auditability**:
   - The forensic "Why?" drawer is rendered entirely from stored SQLite records (`recovery_opportunities`, `scores`, `allocation_decisions`, `authority_checks`, `execution_records`, `ledger_entries`), fulfilling the durable audit trail principle without runtime synthesis.
